# 2026.270.0816 — fix(punktfunk-client): gate the H.264 decode check on a real Vulkan device

## Summary

`punktfunk-client-vulkan-decodes-h264` was an **unconditional hardware-capability assertion**:

```yaml
command: vulkaninfo 2>/dev/null | grep -q VK_KHR_video_decode_h264
```

`vulkaninfo` only advertises `VK_KHR_video_decode_h264` when the venue exposes a **hardware**
Vulkan device. On a venue with none — a plain container host, a headless CI runner, or the
QEMU/Cirrus guest this was surfaced on — `vulkaninfo --summary` enumerates exactly one physical
device (`deviceType = PHYSICAL_DEVICE_TYPE_CPU`, driver `llvmpipe`), the **software** fallback,
which implements zero `VK_KHR_video*` extensions. The grep therefore always exited 1, and the check
reported a **product defect for an absent hardware capability**.

**Root cause (R1):** the check conflated "the client can decode" (a product property) with "this
venue has a hardware GPU" (an environment property), asserting the former with a probe that only
establishes the latter. charly's check grammar has **no per-step conditional-skip primitive**
(`sdk/kit/planrun.go` skips only on `skip: true`, `exclude_distro`, a context mismatch, or an
unresolved variable), so the project's established expression of "hardware absent → not applicable"
is the explicit `N/A` pass used by `candy/cachyos-gpu-desktop-check` ("N/A: no NVIDIA GPU passed
through to this guest"). This is R7a ("live or skip"), gated on the real hardware — never a
mock/fake.

**Fix — gate the assertion on the hardware it actually needs:**

```yaml
stdout:
  contains: VULKAN-H264-OK
context: [runtime]
command:
  command: |
    summary=$(vulkaninfo --summary 2>/dev/null)
    if ! printf '%s' "$summary" | grep -qE 'deviceType[[:space:]]*=[[:space:]]*PHYSICAL_DEVICE_TYPE_(DISCRETE_GPU|INTEGRATED_GPU|VIRTUAL_GPU|OTHER)'; then
      echo "VULKAN-H264-OK (N/A: no hardware Vulkan device in this venue — software llvmpipe or none; hardware H.264 decode is not assertable here)"
      exit 0
    fi
    vulkaninfo 2>/dev/null | grep -q VK_KHR_video_decode_h264 \
      && echo "VULKAN-H264-OK (hardware Vulkan device advertises VK_KHR_video_decode_h264)" \
      || { echo "FAIL: a hardware Vulkan device is present but advertises no VK_KHR_video_decode_h264 — the renderer would advertise codec 0x00" >&2; exit 1; }
```

- no hardware device → visible **N/A**, pass (the environment gate is absent);
- hardware device present but no H.264 → **FAIL** — the real defect the check exists for, so the check
  is not weakened;
- `stdout: contains: VULKAN-H264-OK` anchors the pass to the marker, so a silent success is impossible.

The file is also `charly migrate`d to the current schema (`2026.261.1747`; the current charly
otherwise refuses to validate it) and the candy `version:` bumped, since its content changed.

**Verification-environment note (transparency, not a dismissal).** My first bed attempt reddened the
two `punktfunk:` steps with `no provider registered for plugin verb "punktfunk"`. That failure's own
diagnostic named its mechanism verbatim: `the baked-plugin search path is EMPTY — $CHARLY_PLUGIN_ONLY=1
drops the FHS path and $CHARLY_PLUGIN_DIR is unset`. That is the documented dev/worktree-charly
behaviour — the binary's startup warning says *"Set CHARLY_PLUGIN_DIR to load plugins from a custom
location"* — and a packaged charly finds these plugins on the FHS path instead. Setting
`CHARLY_PLUGIN_DIR` to the built plugin directory (the warning's own remedy) makes both steps pass,
as the green run above shows. It is a verification-setup detail with a named cause and a named fix,
not a repo defect and not a park.
